LANG-0. Общее
LANG-001
Рекомендуется избегать использования аббревиатур, так как в разных сферах одна и та же аббревиатура может иметь различные расшифровки.

Критичность: Низкая

Цели/причины:

Аббревиатуры могут иметь разные значения в разных контекстах, что приводит к недопониманию
Явные названия улучшают читаемость кода и снижают когнитивную нагрузку при работе с кодом
Исключения для общепринятых аббревиатур (MSISDN, BAN) допустимы, так как они являются стандартными терминами в домене
Исключением являются следующие аббревиатуры и сокращения, широко используемые в Службе Разработки:

MSISDN (Mobile Subscriber Integrated Services Digital Number) - номер мобильного абонента для связи в стандартах GSM, UMTS и пр.
BAN (Business Account Number) - Номер лицевого счета в биллинговой системе.
Расширенный список сокращений, которые могут встретиться в проектах, специфичных для НУРТелеком можно найти в документе по Сокращения и аббревиатуры.

Note:
Каждый проект может объявлять свои собственные аббревиатуры и сокращения.

В таком случае все они должны быть описаны как в README.md самого проекта, так и документации к нему (при ее наличии).


LANG-002
120 символов - это предпочтительная длина строки, к которой нужно стремиться.

Критичность: Низкая

Цели/причины:

Длина строки 120 символов оптимальна для комфортного просмотра кода на большинстве мониторов без горизонтальной прокрутки
Единообразие длины строк улучшает читаемость и упрощает code review
Это вопрос субъективный, и важно также стремиться к единообразию. Часто можно узнать больше, посмотрев, как обрабатываются конкретные ситуации в других частях проекта.

Строки от 120 до 140 символов допустимы, но крайне не приветствуются и должны быть немногочисленными.


LANG-003 
При переносе длинного выражения рекомендуется стремиться к длине в 120 символов.

Критичность: Низкая

Цели/причины:

Размещение разделителей в конце строки улучшает визуальное восприятие структуры выражения
Позволяет быстро определить, что строка является продолжением предыдущей, а не новой операцией
Единообразный стиль переноса упрощает чтение сложных выражений и снижает вероятность ошибок при редактировании
Размещать разделители необходимо в конце текущей строки, а не в начале следующей.

В данном контексте следующие символы считаются разделителями: , + ? : && ||

Например:
if (thisLengthyMethodCall(param1, param2) && anotherCheck() &&
        yetAnotherCheck()) {
    // ....
}

static {} блоки

конструкторы

Для внутренних классов дополнительные пустые строки вокруг полей и конструкторов можно не добавлять, поскольку внутренний класс уже отделен двумя строками, если только внутренний класс не является более существенным. LANG-006 
При разработке нового функционала не рекомендуется использовать устаревшие (deprecated) классы и методы.

Критичность: Высокая

Цели/причины:

Deprecated API могут быть удалены в будущих версиях, что приведет к необходимости рефакторинга
Использование актуальных API обеспечивает доступ к улучшениям, исправлениям ошибок и лучшим практикам
Предотвращает накопление технического долга и упрощает миграцию на новые версии библиотек


LANG-007 
В случае, если Вы заменяете использование устаревшего (deprecated) класса или метода в уже существующем коде, рекомендуется создать задачу на рефакторинг данного кода.

Критичность: Средняя

Цели/причины:

Создание отдельной задачи позволяет планировать рефакторинг и оценивать его влияние на систему
Предотвращает смешивание рефакторинга с функциональными изменениями, что упрощает code review и тестирование
Обеспечивает отслеживаемость технического долга и возможность приоритизации его устранения


LANG-1. Пакеты, классы
LANG-101
Не следует помещать весь код в один пакет, даже если на данном этапе и не так много файлов.

Критичность: Высокая

Зло делать один пакет models, а в него класть 10 моделей. Делите внутри на пакеты по доменной модели. Внутри доменных пакетов допускается дополнительное инфраструктурное разделение пакетов (services, models и т.д)

Цели/причины:

Структурирование по пакетам улучшает навигацию и поиск нужных классов
Разделение по доменной модели отражает бизнес-логику и упрощает понимание архитектуры
Предотвращает накопление большого количества файлов в одном пакете, что усложняет поддержку кода


LANG-102
Названия пакетов должны быть в нижнем регистре. Если название пакета состоит из нескольких слов, то необходимо называть в snake_case для улучшения читаемости человеком и единого стиля.

Критичность: Средняя


LANG-103

Критичность: Высокая

Цели/причины:

Соответствие имени файла и класса является стандартом Java и упрощает поиск файлов
Предотвращает путаницу при работе с файловой системой и IDE


LANG-104
Название класса не должно совпадать с именем пакета

Критичность: Высокая

Цели/причины:

Избегает конфликтов имен и неоднозначности при импорте классов

LANG-105

Критичность: Средняя

Классы представляют сущности или концепции, что естественно выражается существительными
Улучшает читаемость кода и делает назначение класса более понятным

Несоответствующий код:
public class ProcessSubscriber {

public class ValidatePhoneNumber {
    // ...

Соответствующий код:
public class SubscriberProcessor {

    // ...

LANG-106
Не создавать "Магические классы" или же "Божественные классы" (т.у. классы, которые собирают в себе множество несвязанных между собой обязанностей). К примеру общий класс Utils.java или Helpers.java

Критичность: Высокая

Цели/причины:

Классы с множественной ответственностью нарушают принцип единственной ответственности (SRP)
Усложняют поддержку и понимание кода
Затрудняют переиспользование и приводят к сильной связанности между компонентами системы

Несоответствующий код:
public class SubscriberUtils {
    public void validatePhoneNumber(String phoneNumber) { }
    public void calculateTariffPrice(Tariff tariff) { }
    public void sendSmsNotification(Subscriber subscriber, String message) { }
    public void formatBalance(BigDecimal balance) { }
    public void parseCallHistory(String data) { }
}

Соответствующий код:
public class PhoneNumberValidator {
    public void validatePhoneNumber(String phoneNumber) { }
}

public class TariffCalculator {
    public void calculateTariffPrice(Tariff tariff) { }
}

public class SmsNotificationService {
    public void sendSmsNotification(Subscriber subscriber, String message) { }
}

public class BalanceFormatter {
    public void formatBalance(BigDecimal balance) { }
}

public class CallHistoryParser {
    public void parseCallHistory(String data) { }
}


LANG-107
Не использовать классы в качестве единого хранилища. К примеру одного класса Constants.java, в котором собраны абсолютно все конфиги и параметры проекта

Критичность: Средняя

Цели/причины:

Единый класс констант становится слишком большим и сложным для навигации
Затрудняет понимание, какие константы относятся к какой функциональности
Нарушает принцип разделения ответственности и усложняет рефакторинг

Несоответствующий код:
public class Constants {
    public static final int MAX_SUBSCRIBER_AGE = 120;
    public static final String DEFAULT_TARIFF_CODE = "BASIC";
    public static final int SMS_MAX_LENGTH = 160;
    public static final String CALL_HISTORY_DATE_FORMAT = "yyyy-MM-dd HH:mm:ss";
    public static final BigDecimal MIN_BALANCE_THRESHOLD = new BigDecimal("0.01");
    public static final int MAX_PHONE_NUMBER_LENGTH = 15;
    public static final String DEFAULT_TIMEZONE = "UTC";
}

Соответствующий код:
public class SubscriberConstants {
    public static final int MAX_SUBSCRIBER_AGE = 120;
    public static final int MAX_PHONE_NUMBER_LENGTH = 15;
}

public class TariffConstants {
    public static final String DEFAULT_TARIFF_CODE = "BASIC";
    public static final BigDecimal MIN_BALANCE_THRESHOLD = new BigDecimal("0.01");
}

public class SmsConstants {
    public static final int SMS_MAX_LENGTH = 160;
}

public class CallHistoryConstants {
    public static final String CALL_HISTORY_DATE_FORMAT = "yyyy-MM-dd HH:mm:ss";
    public static final String DEFAULT_TIMEZONE = "UTC";
}


LANG-108
Не использовать абстрактные названия классов. К примеру, Entity, Object, Instance и т.д.

Критичность: Высокая

Цели/причины:

Абстрактные названия не передают конкретное назначение класса и его роль в системе
Усложняют понимание кода и поиск нужных классов в проекте
Могут конфликтовать с системными классами Java и создавать путаницу


LANG-109
Не использовать цифры в именах классов

Критичность: Средняя

Цели/причины:

Имена с цифрами обычно указывают на плохую структуру кода или отсутствие осмысленных названий
Ухудшают читаемость и не соответствуют общепринятым соглашениям об именовании
Могут создавать проблемы при работе с некоторыми инструментами и системами
Не применяется к цифрам, которые являются частью общепринятых терминов, стандартных обозначений (например, IPv4, HTTP2, HTML5) или номера версий (например, MyClassV2, MyClassV3).


LANG-110
Название класса не должно иметь двусмысленное название и назначение

Критичность: Высокая

Цели/причины:

Двусмысленные названия приводят к неправильному пониманию назначения класса
Усложняют выбор подходящего класса при разработке новых функций
Снижают качество кода и увеличивают вероятность ошибок при использовании класса


LANG-111
Рекомендуемый порядок элементов в java-классе:

Критичность: Низкая

static поля
final поля
non-final поля
конструкторы от самого широкоспециализированного к самому узкоспециализированному
методы (в т.ч. и private), вызываемые из конструкторов
static методы
свойства JavaBean (т. е. геттеры и сеттеры при наличии)
реализации методов интерфейсов или public методы, которые не являются реализацией методов интерфейсов
private или protected методы, которые вызываются из реализаций методов интерфейсов
другие методы
equals, hashCode, toString (при наличии)
Обратите внимание, что private или protected методы, вызываемые из реализаций методов, должны располагаться непосредственно под методами, в которых они используются.

Другими словами, если существует 3 реализации методов интерфейсов с 3 приватными методами (по одному из каждой), то порядок методов должен включать 1 интерфейс и 1 приватный метод последовательно, а не 3 интерфейса и 3 приватных метода внизу.

Цели/причины:

Стандартизированный порядок элементов улучшает навигацию по классу и упрощает его понимание
Логическая группировка (поля, конструкторы, методы) соответствует естественному порядку чтения кода
Размещение связанных методов рядом друг с другом улучшает читаемость и упрощает поддержку

Note:

Прежде всего, организация кода должна быть естественной и логичной для конкретного класса.


LANG-112
Рекомендуется тщательно выбирать место в классе при добавлении нового поля. Его не следует просто добавлять в конец списка имеющихся полей.

Критичность: Низкая

Возможно, поле связан с другими полями или относится к группе - в этом случае его следует разместить рядом со связанными с ним полями.

Цели/причины:

Логическая группировка связанных полей улучшает понимание структуры данных класса
Упрощает навигацию и поиск нужных полей при работе с кодом
Отражает семантические связи между полями и их назначение в контексте класса


LANG-113
Порядок геттеров/сеттеров (при их наличии) должен совпадать с порядком объявления связанных с ними полей.

Критичность: Низкая

Цели/причины:

Соответствие порядка упрощает поиск методов для конкретного поля
Создает предсказуемую структуру класса и улучшает его читаемость
Упрощает навигацию по коду, особенно в классах с большим количеством свойств


LANG-114
Поля дочернего класса не должны затенять поля родительского класса.

Критичность: Высокая

Цели/причины:

Затенение полей создает путаницу и может привести к неожиданному поведению при обращении к полям
Усложняет понимание иерархии классов и наследования

Несоответствующий код:
public class Fruit {
    protected Season ripe;
    protected Color flesh;
    // ...
}
public class Raspberry extends Fruit {
    private boolean ripe;
    private static Color FLESH;
}

Соответствующий код:
public class Fruit {
    protected Season ripe;
    protected Color flesh;
    // ...
}
public class Raspberry extends Fruit {
    private boolean ripened;
    private static Color FLESH_COLOR;
}


LANG-115
Обращение к полю уровня класса всегда должно осуществляться с помощью this

Критичность: Средняя

Цели/причины:

Явное указание this устраняет неоднозначность между полями класса и локальными переменными
Улучшает читаемость кода и делает намерение разработчика более понятным
Предотвращает случайное затенение полей локальными переменными с теми же именами Уточнение по исключениям:
Допускается обращение без this к явно распознанным DI-зависимостям: - полям с @Autowired, @Inject, @Resource, @Named - collaborator-полям, инициализируемым через constructor injection - collaborator-полям в Spring-бинах с @RequiredArgsConstructor - Обычные value-поля вроде Integer, Long, String, BigDecimal и другие поля состояния не считаются зависимостями только потому, что они пришли через конструктор

Для таких полей this обязателен

Несоответствующий код:
@Service
@RequiredArgsConstructor
class FooService {
private final ObjectMapper objectMapper;
private final Integer retryCount;

    void process() {
        objectMapper.writeValueAsString("ok");
        retryCount.toString();

        String status = "ACTIVE";
        status = "DONE";
    }
}

Соответствующий код:
@Service
@RequiredArgsConstructor
class FooService {
private final ObjectMapper objectMapper;
private final Integer retryCount;

    void process() {
        objectMapper.writeValueAsString("ok");
        this.retryCount.toString();

        this.status = "DONE";
    }
}


LANG-116
Не рекомендуется использовать package-private (дефолтный) уровень доступа для полей класса. Предпочтительнее явно указывать уровень доступа, чтобы избежать непредвиденных изменений.

Критичность: Средняя

Цели/причины:

Явное указание уровня доступа делает намерения разработчика понятными и предотвращает случайные изменения
Package-private доступ может привести к нежелательной связанности между классами в одном пакете
Улучшает инкапсуляцию и делает код более безопасным и предсказуемым


LANG-117
Не рекомендуется создавать слишком много методов в одном классе.

Критичность: Средняя

Если класс содержит более 10 методов, следует рассмотреть возможность его разделения на более мелкие и специализированные классы.

Цели/причины:

Усложняет понимание и поддержку класса, увеличивая когнитивную нагрузку


LANG-118
Не рекомендуется объявлять анонимные классы, содержащие более 15 строк.

Критичность: Средняя

При превышении разумного размера лучше выделить отдельный именованный класс

Цели/причины:

Анонимные классы с большим объемом кода ухудшают читаемость основного класса


LANG-119
Не рекомендуется запускать потоки в конструкторе класса.

Критичность: Высокая

Проблема с вызовом Thread.start() в конструкторе заключается в том, что при наследовании данного класса конструктор суперкласса запустит поток до того, как дочерний класс будет по-настоящему инициализирован.

Несоответствующий код:
public class MyClass {
    Thread thread = null;
    public MyClass(Runnable runnable) {
        thread = new Thread(runnable);
        thread.start();
    }
}

LANG-223
Для статического nullability-анализа должны использоваться только аннотации JSpecify. Аннотация @NotNull допускается только из jakarta.validation.constraints.

Цели/причины:

У nullability-контракта должна быть одна семантика по всему проекту
org.jspecify.annotations.* предназначены для статического nullability-анализа
jakarta.validation.constraints.NotNull предназначена для runtime-валидации входных данных
Смешивание lombok.NonNull, org.jetbrains.annotations.NotNull, javax.validation.constraints.NotNull и других аналогов делает код неоднозначным
Разделение JSpecify и Jakarta Validation упрощает чтение кода, анализ Sonar и договоренности команды
Правило использования:

Для статического анализа использовать JSpecify
Предпочтительный стиль:

@NullMarked на уровне пакета или класса
@Nullable для исключений
@NonNull из JSpecify только там, где он действительно нужен
@NotNull использовать только как jakarta.validation.constraints.NotNull
@NotNull не использовать для внутренних service/domain-контрактов, если это не Bean Validation boundary

Несоответствующий код:

import org.jetbrains.annotations.NotNull;

    @NotNull
    String loadName(@NonNull String userId) {
        return userId;
    }
}

Соответствующий код:
@NullMarked
package com.example.user;

import org.jspecify.annotations.NullMarked;

import jakarta.validation.constraints.NotNull;
import org.jspecify.annotations.Nullable;

record CreateUserRequest(
        @NotNull String name
) {
}

class UserService {

    String normalize(String id, @Nullable String suffix) {
        return suffix == null ? id : id + suffix;
    }
}

Пояснение:

JSpecify отвечает за типовой nullability-контракт
Jakarta Validation отвечает за валидацию входных данных
Если аннотация означает “это nullable/non-null для анализа типов”, это JSpecify
Если аннотация означает “это поле должно быть провалидировано на входе”, это Jakarta Validation

LANG-603
Рекомендуется использовать EnumMap вместо HashMap, когда ключами являются элементы перечисления.

Критичность: Средняя

Цели/причины:

EnumMap оптимизирован для enum-ключей и обеспечивает лучшую производительность, чем HashMap

Несоответствующий код:
public enum Color {
    RED, GREEN, BLUE, ORANGE;
}
Map<Color, String> colorMap = new HashMap<>();

Соответствующий код:
public enum Color {
    RED, GREEN, BLUE, ORANGE;
}
Map<Color, String> colorMap = new EnumMap<>(Color.class);

LANG-802
Не рекомендуется коммитить в git закомментированный код. Если код больше не нужен, его требуется удалить.

Критичность: Средняя

Цели/причины:

Закомментированный код загромождает файлы и ухудшает читаемость
История Git сохраняет все версии кода, поэтому удаленный код можно восстановить при необходимости
Удаление неиспользуемого кода поддерживает чистоту кодовой базы и упрощает навигацию

LANG-804
Рекомендуется использовать комментарии для объяснения "почему" ("для получения какого результата") что-то делается, а не "что" делается.

Критичность: Высокая

Цели/причины:

Код сам показывает "что" делается, комментарии должны объяснять контекст и причины решений
Понимание "почему" помогает разработчикам принимать правильные решения при изменении кода
Объяснение бизнес-логики и неочевидных решений улучшает поддерживаемость кода

Несоответствующий код:
public BigDecimal calculateCallCost(Long subscriberId, int duration) {
    // Получаем абонента
    Subscriber subscriber = subscriberRepository.findById(subscriberId);
    // Получаем тарифный план
    PricePlan pricePlan = subscriber.getPricePlan();
    // Умножаем стоимость минуты на длительность
    return pricePlan.getCallRate().multiply(BigDecimal.valueOf(duration));
}

Соответствующий код:
public BigDecimal calculateCallCost(Long subscriberId, int duration) {
    Subscriber subscriber = subscriberRepository.findById(subscriberId);
    PricePlan pricePlan = subscriber.getPricePlan();

    // Округление до целых минут в большую сторону согласно тарифному плану,
    // чтобы избежать дробных значений в биллинге
    int roundedMinutes = (int) Math.ceil(duration / 60.0);
    return pricePlan.getCallRate().multiply(BigDecimal.valueOf(roundedMinutes));
}


LANG-805
Рекомендуется сопровождать комментариями блоки кода, в которых происходит что-то из нижеперечисленного:

Критичность: Высокая

сложные stream-цепочки с множественными преобразованиями и фильтрациями
калькуляции с несколькими шагами и с использованием различных формул
алгоритмы с несколькими ветвлениями и условиями
Цели/причины:

Сложные конструкции требуют дополнительного объяснения для понимания логики и намерений
Комментарии помогают быстро понять назначение сложных вычислений без детального анализа кода
Упрощают рефакторинг и поддержку сложных алгоритмов, снижая риск ошибок

Соответствующий код:
public List<Subscriber> findEligibleSubscribersForPromotion() {
    return subscriberRepository.findAll().stream()
            // Отбираем только активных абонентов с достаточным балансом
            .filter(Subscriber::isActive)
            .filter(s -> s.getBalance().compareTo(new BigDecimal("100")) > 0)
            .filter(s -> s.getPricePlan() != null)
            // Ищем абонентов, которые недавно прекратили активность (30-90 дней назад),
            // чтобы предложить им специальные условия для возврата
            .map(s -> {
                LocalDate lastPaymentDate = s.getLastPaymentDate();
                if (lastPaymentDate == null) {
                    return null;
                }
                long daysSinceLastPayment = ChronoUnit.DAYS.between(lastPaymentDate, LocalDate.now());
                if (daysSinceLastPayment > 30 && daysSinceLastPayment < 90) {
                    return s;
                }
                return null;
            })
            .filter(Objects::nonNull)
            .collect(Collectors.toList());
}

public BigDecimal calculateMonthlyBill(Long subscriberId, int callMinutes, int smsCount, int dataMB) {
    Subscriber subscriber = subscriberRepository.findById(subscriberId);
    PricePlan plan = subscriber.getPricePlan();

    // Расчет базовой стоимости услуг по тарифному плану
    BigDecimal callCost = plan.getCallRate().multiply(BigDecimal.valueOf(callMinutes));
    BigDecimal smsCost = plan.getSmsRate().multiply(BigDecimal.valueOf(smsCount));
    BigDecimal dataCost = plan.getDataRate().multiply(BigDecimal.valueOf(dataMB));
    BigDecimal subtotal = callCost.add(smsCost).add(dataCost);

    // Применение скидки в зависимости от уровня лояльности:
    // GOLD - 10%, SILVER - 5%, остальные - без скидки
    BigDecimal discount = BigDecimal.ZERO;
    if (subscriber.getLoyaltyLevel() == LoyaltyLevel.GOLD) {
        discount = subtotal.multiply(new BigDecimal("0.1"));
    } else if (subscriber.getLoyaltyLevel() == LoyaltyLevel.SILVER) {
        discount = subtotal.multiply(new BigDecimal("0.05"));
    }

    return subtotal.subtract(discount);
}


LANG-806
TODO комментарии нежелательны в коде. Для отслеживания необходимых доработок рекомендуется использовать систему трекинга задач Jira.

Критичность: Высокая

Цели/причины:

TODO комментарии часто забываются и накапливаются в коде, создавая технический долг
Удаление TODO из кода поддерживает чистоту кодовой базы и фокусирует внимание на актуальных задачах
Исключением может служить ситуация, когда проект находится в стадии MVP.

Warning:
После завершения стадии MVP, все TODO комментарии должны быть удалены из кода.

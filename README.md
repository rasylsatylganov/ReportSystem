# Универсальная система отчётности

Java 21, Maven, Spring Boot 3.5.6, Oracle. Проект содержит два Maven-модуля.

| Модуль | Содержимое |
|---|---|
| `common` | Entity, репозитории и сервисы системы отчётности |
| `web-api` | REST-контроллеры, DemoApplication, настройки и тест приложения |

Зависимость: `web-api` использует `common`. Корневой POM объединяет модули.
`common` собирается в обычный JAR, `web-api` — в запускаемый Spring Boot JAR.

## Модели и сущности

JPA-сущности находятся в `common/.../entity` и имеют суффикс `Entity`.
Контроллеры и публичные интерфейсы сервисов используют records из
`common/.../model`: например, `DrTypePeriod` для ответа и
`DrTypePeriodRequest` для создания или изменения записи.

Преобразование выполняют классы `...Mapper` из `common/.../mapper`.
Сервисы вызывают их внутри своих транзакций и отвечают за операции с
репозиториями. В ответах связанные записи представлены вложенными моделями;
мапперы преобразуют JPA-связи, не обращаясь к другим сервисам.
В запросах связи задаются через `IdReference`, например
`"typePeriod": {"id": 1}`. `JpaReferenceResolver` получает управляемую JPA-ссылку по ID;
остальные поля вложенного объекта не изменяют связанную запись.

ID новой записи назначает backend; при обновлении используется ID из URL.
Порядок типов периодов также назначает backend: входная модель не содержит
`sortIndex`. Названия полей JSON и URL существующих маршрутов сохранены.

## Валидация запросов и ошибки API

Входные records `...Request` проверяются через Jakarta Bean Validation
и `@Valid` в контроллерах. Проверяются обязательные значения, длины строк,
точность чисел, положительные ID и номера строк/столбцов, вложенные ссылки.
Дата окончания периода не может быть раньше начала; диапазон строк импорта
также должен иметь согласованные границы.

Ошибки обрабатывает `web-api/.../exception/GlobalExceptionHandler`.
Все ответы об ошибках имеют поля `code` и `message`, например:

```json
{"code":"VALIDATION_ERROR","message":"Поле «Код типа периода» обязательно."}
```

HTTP-статусы: 400 — ошибка запроса, 404 — ресурс не найден,
409 — конфликт ограничений данных, 500 — неожиданная ошибка сервера.
Некорректные методы и Content-Type возвращают соответственно 405 и 415.
Сообщения для клиента не содержат stack trace или деталей SQL/БД.
Доменная ошибка отсутствия записи представлена `ResourceNotFoundException`,
некорректной внутренней ссылки — `InvalidRequestException`.

## Oracle

Все 13 JPA-сущностей наследуют `BaseEntity` с полями `createdAt` и
`updatedAt`, которые хранятся в столбцах `CREATED_AT` и `UPDATED_AT`.
При вставке обе даты заполняются одинаковым текущим временем; при
изменении обновляется только `updatedAt`. Используется `Asia/Bishkek`.
Заполнение выполняют JPA callbacks `@PrePersist` / `@PreUpdate`.

Перед первым запуском этой версии остановите backend и выполните
`docs/sql/001_add_audit_timestamps.sql` в той же схеме Oracle, к которой
подключается приложение (SQL Developer: Run Script / F5; также SQLcl/SQL*Plus).
Скрипт добавляет столбцы `TIMESTAMP(6)`, заполняет пустые значения у старых
записей и устанавливает `NOT NULL`. Для старых записей без дат используется
время миграции: фактическое время их создания восстановить невозможно.
Повторное выполнение сохраняет уже заполненные даты. Oracle DDL выполняет
автоматический commit, поэтому миграция не является одной транзакцией.

Прямые SQL-операции и массовые JPQL-обновления обходят JPA callbacks:
при таких операциях даты нужно заполнять явно. Поля аудита не принимаются
во входных Request-моделях и не добавлены в текущие JSON-ответы.

Исходный `application.properties` без изменения содержимого перенесён в
`web-api/src/main/resources/application-local.properties`.
Он подключается автоматически через `spring.config.import`; активировать
профиль вручную не требуется. Исходные настройки подключения и JPA сохранены.

Локальный файл исключён из Git. После клонирования репозитория на другом
компьютере создайте его по образцу `application-local.properties.example`
или восстановите собственную локальную конфигурацию.
Файл-пример использует переменные `ORACLE_JDBC_URL`, `ORACLE_USERNAME`,
`ORACLE_PASSWORD`.

## Сборка и запуск

Все команды выполняются из корневой папки, где находятся оба модуля.
Требуются установленные JDK 21 и Maven, доступ к Maven-репозиториям.

Сборка без запуска исходного теста, подключающегося к Oracle:

```shell
mvn clean package -DskipTests
java -jar web-api/target/web-api-0.0.1-SNAPSHOT.jar
```

Полная сборка с исходным `@SpringBootTest` (требует доступную Oracle
и корректную конфигурацию):

```shell
mvn clean install
```

Запуск из Maven после установки модулей:

```shell
mvn install -DskipTests
mvn -pl web-api spring-boot:run
```

При первом запуске из IDE Maven-проекты должны быть импортированы вместе.

## Пагинация справочников

`GET /api/dr-enterprises`, `/api/dr-periods`, `/api/dr-references`,
`/api/dr-reference-items`, `/api/dr-type-periods` и `/api/dr-type-enterprises`
принимают query-параметры `page` (от 0, по умолчанию 0)
и `size` (от 1 до 100, по умолчанию 20). Записи всех шести справочников
выбираются страницами в БД с сортировкой по `sortIndex`, затем `id`.
Некорректные параметры дают HTTP 400.

Пример: `GET /api/dr-enterprises?page=0&size=20`.

Ответ содержит `content` (массив моделей), `page`, `size`, `totalElements`
и `totalPages`. Пустая коллекция имеет `totalPages: 0`; страница за пределами
списка возвращает HTTP 200 с пустым `content` и фактическими итогами.
Это изменение контракта: потребителям всех шести маршрутов нужно читать
`content` вместо массива в корне ответа и запрашивать необходимые страницы.

Все шесть страниц справочников загружают данные по страницам,
показывают общее количество записей и предлагают размер страницы 10, 20, 50 или 100
(по умолчанию 20). Перемещение записи через границу страницы открывает целевую
страницу; удаление последней записи страницы возвращает на существующую страницу.

## Справочник типов предприятий

На frontend в меню «Справочники → Типы предприятий» добавлена страница
`/type-enterprises`: создание, редактирование, удаление, серверная пагинация
и перестановка записей вверх/вниз. Код ограничен 50 символами, наименование — 200.

Перед запуском обновленного backend остановите его экземпляры и выполните
в Oracle-схеме приложения `docs/sql/002_add_type_enterprise_sort_index.sql`.
Скрипт добавляет `DR_TYPE_ENTERPRISE.SORT_INDEX NUMBER(19,0) NOT NULL`,
заполняет отсутствующие значения из `ID` и подготавливает последовательность
`DR_TYPE_ENTERPRISE_SORT_SEQ` выше максимального существующего индекса.
Повторный запуск сохраняет заполненные индексы и не перемещает последовательность назад.
Oracle DDL автоматически фиксирует изменения; миграция не является единой транзакцией.

Поле `sortIndex` возвращается в модели, назначается сервером и не редактируется
через POST/PUT. Новые записи добавляются в конец. Для перестановки используются
`POST /api/dr-type-enterprises/{id}/move-up` и `.../{id}/move-down`.
Операции изменения блокируют записи справочника в порядке ID в транзакции;
перестановка сохраняет обе измененные записи явно. Граница списка возвращает 204
без изменения данных; отсутствующая запись — 404; конфликт данных — 409.

## Справочники DR_REFERENCE

Страница `/references` находится в меню
«Справочники → Справочники → Справочники». Существующие пункты типов периодов
и предприятий сохранены. Страница поддерживает создание, редактирование,
удаление, серверную пагинацию и изменение порядка вверх/вниз.
Код ограничен 50 символами, наименование — 300.

Перед запуском обновленного backend остановите его экземпляры и выполните
в Oracle-схеме приложения `docs/sql/003_add_reference_sort_index.sql`.
Он добавляет `DR_REFERENCE.SORT_INDEX NUMBER(19,0) NOT NULL`, заполняет
незаполненные индексы значением ID и подготавливает `DR_REFERENCE_SORT_SEQ`
выше максимального индекса. Повторный запуск сохраняет заполненные индексы
и не перемещает последовательность назад. Oracle DDL автоматически фиксирует изменения.

Порядок назначается сервером: новые записи добавляются в конец, обычное
редактирование не меняет индекс. Перестановка выполняется через
`POST /api/dr-references/{id}/move-up` и `.../{id}/move-down`,
в том числе между страницами. Ответ — 204; отсутствующая запись — 404.
Удаление используемого справочника или другой конфликт данных возвращает 409.
Для операций записи используются транзакции и блокировки записей в порядке ID;
перестановка явно сохраняет обе измененные записи.

## Периоды DR_PERIOD

Страница `/periods` открывается через «Справочники → Периоды → Периоды».
Поддерживает создание, редактирование, удаление с подтверждением и серверную
пагинацию. Тип периода выбирается по наименованию в списке с поиском;
список загружает все страницы типов. Выбранный фильтр подставляется в новую запись.
При отсутствии типов страница предлагает сначала создать тип периода.

`GET /api/dr-periods` принимает необязательный положительный `typePeriodId`.
Фильтрация выполняется в БД до пагинации; количество записей относится к фильтру.
Без параметра возвращаются все периоды. Несуществующий тип дает пустую страницу.
Код ограничен 20 символами и уникален в пределах типа, наименование — 200.
Даты обязательны, дата окончания не может быть раньше даты начала.
Календарные даты передаются в формате `YYYY-MM-DD` без преобразования часового пояса.
Перед запуском обновленного backend остановите его экземпляры и выполните
`docs/sql/004_add_period_sort_index.sql` в Oracle-схеме приложения.
Скрипт добавляет `DR_PERIOD.SORT_INDEX NUMBER(19,0) NOT NULL`, заполняет
отсутствующие значения из ID и создает `DR_PERIOD_SORT_SEQ` выше максимального индекса.
Повторный запуск сохраняет заполненные индексы и не перемещает последовательность назад.
Oracle DDL автоматически фиксирует изменения.

Список периодов сортируется по `sortIndex`, затем `id`. Индекс назначает сервер:
новые периоды добавляются в конец, обычный PUT сохраняет индекс, в том числе
при изменении типа. Кнопки вверх/вниз вызывают
`POST /api/dr-periods/{id}/move-up` и `.../move-down`.
Необязательный `typePeriodId` ограничивает выбор соседней записи выбранным типом;
порядок остается общим. Без фильтра перемещение меняет соседей общего списка.
На границе списка возвращается 204 без изменений, отсутствующий период или
несоответствие фильтру — 404. Перестановка работает между страницами;
frontend открывает страницу перемещенной записи. Записи блокируются в порядке ID,
обе измененные записи сохраняются явно в одной транзакции.
Для совместимости с Oracle 12.1 запрос страницы не соединяет период и тип:
связанные типы загружаются отдельно пакетами до 100 записей. Это исключает
ORA-00918 при сочетании пагинации и одинаковых имен столбцов в двух таблицах.

## Предприятия DR_ENTERPRISE

Страница `/enterprises` открывается через «Справочники → Предприятия → Предприятия».
Поддерживает создание, редактирование, удаление с подтверждением, серверную пагинацию,
фильтр по типу предприятия и изменение порядка вверх/вниз.
Тип выбирается по наименованию в списке с поиском; загружаются все страницы типов.
Выбранный в фильтре тип подставляется при создании. Код обязателен, ограничен
20 символами и уникален во всем справочнике; наименование обязательно, до 300 символов.

Перед запуском обновленного backend остановите его экземпляры и выполните
`docs/sql/005_add_enterprise_sort_index.sql` в Oracle-схеме приложения.
Скрипт добавляет `DR_ENTERPRISE.SORT_INDEX NUMBER(19,0) NOT NULL`, заполняет
отсутствующие значения из ID и подготавливает `DR_ENTERPRISE_SORT_SEQ` выше
максимального индекса. Повторный запуск сохраняет заполненный порядок и не
перемещает последовательность назад. Oracle DDL автоматически фиксирует изменения.

`GET /api/dr-enterprises` принимает необязательный положительный `typeEnterpriseId`.
Фильтрация выполняется в БД до пагинации. Сортировка — по `sortIndex`, затем `id`.
Новые записи добавляются в конец; обычное редактирование сохраняет порядок,
в том числе при изменении типа. `POST /api/dr-enterprises/{id}/move-up` и
`.../move-down` принимают тот же необязательный фильтр: с ним выбирается сосед
выбранного типа, без него — сосед общего списка. На границе списка возвращается
204 без изменений; отсутствующее предприятие или несоответствие типу — 404.
Перемещение через границу страницы открывает целевую страницу.
Записи блокируются по ID, обе измененные записи сохраняются явно в транзакции.
Типы загружаются отдельно пакетами до 100 записей для совместимости с Oracle 12.1.

## Значения справочников DR_REFERENCE_ITEM

Страница `/reference-items` открывается через
«Справочники → Справочники → Значения справочников». Поддерживает создание,
редактирование, удаление с подтверждением, серверную пагинацию и стрелки порядка.
Справочник выбирается по наименованию в списке с поиском; загружаются все страницы.
Выбранный фильтр подставляется в форму создания. Код обязателен, до 100 символов,
уникален в пределах справочника. Наименование обязательно, до 300 символов.

Перед запуском обновленного backend остановите его экземпляры и выполните
`docs/sql/006_add_reference_item_sort_index.sql` в Oracle-схеме приложения.
Скрипт **переименовывает** `DR_REFERENCE_ITEM.ORDER_SORT` в `SORT_INDEX`,
расширяет тип до `NUMBER(19,0) NOT NULL` и подготавливает `DR_REFERENCE_ITEM_SORT_SEQ`.
Если индексы заполнены и уникальны, их значения сохраняются. Иначе индексы
перенумеровываются по прежнему порядку `ORDER_SORT NULLS LAST, ID`, сохраняя
относительный порядок записей и устраняя пустые и повторяющиеся значения.
Повторный запуск сохраняет порядок и не перемещает последовательность назад.
При одновременном наличии обоих столбцов скрипт останавливается для их сверки.
Oracle DDL автоматически фиксирует изменения.

API меняется: вместо `orderSort` ответ содержит `sortIndex`; индекс назначает сервер,
POST/PUT принимают только `reference: {id}`, `codeReferenceItem`, `nameReferenceItem`.
Присланные клиентом `id`, `orderSort` или `sortIndex` игнорируются. Новая запись
добавляется в конец, обычное редактирование сохраняет порядок, включая смену справочника.
Другие таблицы с `ORDER_SORT` эта миграция не затрагивает.

`GET /api/dr-reference-items` принимает необязательный положительный `referenceId`.
Фильтрация выполняется в БД до пагинации; сортировка — по `sortIndex`, затем `id`.
`POST /api/dr-reference-items/{id}/move-up` и `.../move-down` принимают тот же фильтр.
С фильтром выбирается сосед внутри справочника, без него — сосед общего списка.
На границе списка — 204 без изменений; отсутствующая запись или несовпадение
справочника — 404. Перемещение между страницами открывает целевую страницу.
Записи блокируются по ID, обе переставленные записи сохраняются явно в транзакции.
Связанные справочники загружаются отдельно пакетами для совместимости с Oracle 12.1.

## Конструктор входящих отчётов

Пункт «Входящие отчёты» открывает `/incoming-reports`: список с пагинацией,
создание, открытие и удаление отчёта без загруженных данных.
Над списком расположена панель «Фильтр» с одиночным выбором типа периода
и типа предприятия. По умолчанию выбираются первые значения; варианта «Все» нет.
Оба условия применяются совместно в БД до пагинации, включая подсчёт записей.
Смена фильтра возвращает на первую страницу; обновление и удаление сохраняют выбор.
Конструктор находится по `/incoming-reports/new` и `/incoming-reports/{id}`.
Основные параметры заполняют `MD_REPORT_IN`. Слева задаются справочники
`MD_REPORT_IN_REFERENCE`: расположение и координата строки/столбца Excel.
В горизонтальную шапку добавляются поля `MD_REPORT_IN_REFERENCE_ITEM`:
значение справочника, тип данных, номер столбца, порядок и флажок обязательности.
`IS_REQUIRED` сохраняется как 0/1 и предназначен для проверки обязательных
данных будущим импортом. Конструктор не импортирует Excel и не записывает `TB_*`.

Центральный предпросмотр строится из метаданных: буквы/номера столбцов,
строки шапки, примеры значений вертикальных справочников и обозначения типов
полей. Группировка примера иллюстративная, рабочие значения не сохраняются.
Нажатие на элемент структуры или столбец открывает настройки справа.
Порядок отображения и координаты Excel независимы: кнопки «Выше/Ниже» меняют
только `ORDER_SORT` метаданных. Изменения локальны до нажатия «Сохранить»;
при уходе со страницы с изменениями показывается предупреждение.

`/api/incoming-report-templates`:

- `GET ?page=0&size=20&typePeriodId=1&typeEnterpriseId=1` — список отчётов;
  размер 1–100, сортировка по ID. Оба фильтра необязательны в API,
  должны быть положительными и при совместной передаче соединяются условием И;
- `GET /{id}` — отчёт, справочники, поля и `revision`;
- `GET /lookups` — расположения и типы данных;
- `POST /validate` — проверка полной структуры без сохранения;
- `POST` — создание трёх групп метаданных одной транзакцией, ответ 201;
- `PUT /{id}` — сохранение с `revision` из последнего GET;
- `DELETE /{id}` — удаление отчёта и его структуры, если нет загруженных данных.

Справочники формы и поля не должны повторяться. Поле принадлежит добавленной
горизонтальной шапке. Столбцы вертикальных справочников и полей не пересекаются.
Диапазон строк ограничен Excel: 1–1048576, столбцы — 1–16384. Поддерживаются
NUMBER, STRING, DATETIME. Пустая горизонтальная шапка не сохраняется.
Существующие ограничения «один справочник/одно значение один раз в отчёте» сохранены.
Активация и версии шаблонов пока не реализуются.

При обновлении сохраняются существующие ID метаданных. Чужие ID и замена
привязки справочника/значения под тем же ID отклоняются. Для замены нужно удалить
элемент и добавить новый. Удаление используемых метаданных и изменение типа поля
с уже загруженными значениями запрещены (409). Конфликт кода или любая ошибка
откатывает всю транзакцию. Корневой отчёт блокируется при записи; `revision`
проверяется по снимку структуры и связанных справочников и защищает от перезаписи
устаревшего экрана. После 409 нужно перечитать отчёт.
Изменение схемы БД для конструктора не требуется.

### Защита метаданных после сдачи отчётов

Если для пары «Тип периода + Тип предприятия» есть хотя бы одна реальная ячейка
в `TB_REFERENCE_ITEM_VALUE` за любой период, **все формы этой пары** доступны только
для просмотра. Создание (включая копирование в эту пару), изменение и удаление
отчётов, их справочников и полей запрещены. При переносе формы или элемента
проверяются исходная и целевая пары. Копирование из защищённой пары в свободную разрешено.

Наличие данных определяется так же, как во «Входящих отчётах»: обе группы метаданных
ячейки должны принадлежать одной форме, а типы периода и предприятия — соответствовать
форме. Одни маркеры `TB_REFERENCE_ITEM` и пустые шаблоны блокировку не включают.
Пары без реальных ячеек остаются редактируемыми. Проверка выполняется при каждой
операции записи; попытка изменить защищённые метаданные возвращает HTTP 409
с кодом `DATA_CONFLICT` и объяснением. Чтение и проверка структуры без сохранения доступны.

`GET /api/incoming-report-templates/metadata-access?typePeriodId=1&typeEnterpriseId=1`
возвращает `{ "readOnly": true, "reason": "…" }` для защищённой пары либо
`{ "readOnly": false, "reason": null }` для свободной. Оба ID обязательны и положительны;
неизвестный тип возвращает 404. Ответ `GET /api/incoming-report-templates/{id}`
дополнен полями `readOnly` и `readOnlyReason`; состояние доступа не входит в `revision`.

Список и конструктор показывают причину блокировки и отключают операции изменения.
Выбор элементов структуры, просмотр свойств и предпросмотр продолжают работать.
Блокировка вычисляется по текущим данным; отдельный постоянный статус не хранится.
Обновление требует перезапуска backend и обновления frontend, миграция БД не нужна.

## Просмотр входящих отчётов

Меню «Отчёты → Входящие» открывает `/reports/incoming`. Сверху слева в одной
узкой панели расположены вертикальные списки типов периодов и предприятий
с галочками; изначально выбран первый тип каждого списка. Справа автоматически
загружается общая таблица «Период + Предприятие». Поиск по периоду, названию
или коду предприятия обновляет таблицу после короткой паузы ввода.
Кнопки «Найти отчёты» нет. Фильтрация, подсчёт и пагинация выполняются в БД.

Таблица содержит только сочетания с записями ячеек `TB_REFERENCE_ITEM_VALUE`,
связанными с тем же отчётом через обе группы метаданных и совместимыми типами.
Пустые шаблоны и одни маркеры шапки в `TB_REFERENCE_ITEM` сдачей не считаются.
Это признак наличия загруженных данных, а не отдельный статус утверждения отчёта.
Нажатие строки загружает сданные формы выбранного предприятия за период в узкую
панель слева во второй строке. Нажатие формы показывает её данные справа;
выбранная строка и форма подсвечиваются. Смена фильтров сбрасывает прежний просмотр.

`GET /api/incoming-reports/submissions?typePeriodIds=1,2&typeEnterpriseIds=1,2&page=0&size=20`
возвращает страницу уникальных сочетаний периода и предприятия. Оба списка
обязательны, содержат 1–100 положительных ID; необязательный `search` — до 300
символов. Периоды упорядочены по дате начала и ID по убыванию, предприятия —
по порядку справочника и ID. `GET /api/incoming-reports/submitted-templates?periodId=1&enterpriseId=1&page=0&size=20`
возвращает только формы с ячейками для выбранного сочетания, по ID отчёта.
В обоих случаях `page` начинается с 0, `size` ограничен 1–100.
Изменение схемы БД не требуется; после обновления нужен перезапуск backend.

Просмотр читает реальные данные из `TB_REFERENCE_ITEM` и `TB_REFERENCE_ITEM_VALUE`,
не изменяя метаданные и данные. Импорт Excel заполняет эти же рабочие таблицы.

`GET /api/incoming-reports/{id}?periodId=1&enterpriseId=1&page=0&size=20`
возвращает описание столбцов и страницу строк. `page` начинается с 0,
`size` ограничен 1–100. Период и предприятие обязательны и должны соответствовать
типам отчёта: несовпадение даёт 400, отсутствующая запись — 404.

Пагинация выполняется в Oracle: сначала выбираются уникальные номера строк
с данными или вертикальными группами и подсчитывается их количество, затем
загружаются значения только для номеров текущей страницы. Горизонтальные
маркеры шапки не становятся строками данных. Для вертикальных групп читаются
маркеры страницы и последний предшествующий маркер каждой группы. При смене
внешней группы вложенные группы сбрасываются; на новой странице продолжающаяся
группа повторяется. Неоднозначные дубликаты одной ячейки дают 409.

Порядок столбцов и группировки берутся из метаданных. Отображение соответствует
первым верхним формам `docs/excel/Таблица №1.xlsx` — `Таблица №4.xlsx`, включая
объединённые вертикальные группы. Числа передаются строками для сохранения
точности `NUMBER(28,6)`, даты отображаются без сдвига часового пояса.
Нижние альтернативные представления №2.1, №3.1 и другие не используются.

Для больших объёмов выполните `docs/sql/008_add_incoming_report_view_indexes.sql`
в Oracle-схеме приложения. Он добавляет индексы для выборки групп по периоду,
предприятию и метаданным и значений по полю и строке. Данные не меняются;
DDL Oracle автоматически фиксируется. Скрипт автоматически не запускается.

## Импорт входящих отчётов Excel

На странице «Отчёты → Входящие» (`/reports/incoming`) кнопка «Загрузить Excel»
открывает выбор `.xlsx` до 20 МБ. После выбора кнопка «Импортировать» отправляет
файл; по завершении показываются период, предприятие, строки и значения по листам.
Список сданных отчётов обновляется с типами импортированного файла.

Имя файла: `<CODE_TYPE_PERIOD>_<CODE_PERIOD>_<CODE_TYPE_ENTERPRISE>_<CODE_ENTERPRISE>.xlsx`.
Например, `QUA_2026Q02_BANK_1000001.xlsx` относится к квартальному типу,
периоду `2026Q02` (II квартал 2026), типу предприятий `BANK` и предприятию `1000001`.
Коды ищутся без учёта регистра; начальные нули кода предприятия сохраняются.
Тип периода содержит 3 символа, код периода и предприятия — до 20, тип предприятия —
до 50; разрешены латинские буквы, цифры и дефис. `_` разделяет ровно четыре кода.
Период и предприятие должны заранее существовать в соответствующих справочниках;
импорт не создаёт их и не определяет отчётный период по датам внутри ячеек.

Имя каждого листа равно `MD_REPORT_IN.CODE_REPORT_IN` в паре типов из имени файла,
например `R01`. Обрабатываются все листы, включая скрытые; неизвестный лист,
повторение одной формы или отсутствие её структуры отклоняет весь файл.
Можно загрузить часть форм пары; книга содержит от 1 до 100 листов.

Метаданные задают расположение и координаты шапок и вертикальных справочников,
столбцы, порядок, типы и обязательность полей. Наименования из Excel сопоставляются
с `DR_REFERENCE_ITEM.NAME_REFERENCE_ITEM` **только внутри справочника метаданных**,
без регистра и пробелов по краям. Сопоставление по коду пока не используется.
Неизвестные или неоднозначные названия отклоняются; новые значения не создаются.
Заголовок каждого настроенного поля должен соответствовать его значению справочника.

Сканирование ограничено `INDEX_ROW_SCAN_BEGIN` и `INDEX_ROW_SCAN_END` включительно.
Строки до окончания настроенных горизонтальных шапок пропускаются: при начале 2
и шапке 2 данные читаются с 3. Ведущий столбец — первый вертикальный справочник
по `ORDER_SORT`, затем ID; если вертикальных справочников нет — первое поле первой
горизонтальной шапки по тому же порядку. Это соответствует порядку конструктора.
Первая пустая ячейка ведущего столбца завершает лист; нижние строки не импортируются.
Нулевое числовое значение не считается пустым. Верхняя ячейка объединения действует
во всех строках объединённой области. Пустая ячейка другого обязательного поля — ошибка.
Лист без значений данных отклоняется.

Поддерживаются `NUMBER` (`NUMBER(28,6)`, без округления переполнения), `STRING`
(до 2000 символов) и `DATETIME` (дата Excel, `ДД.ММ.ГГГГ`, `ГГГГ-ММ-ДД`,
также со временем). Числа в строках допускают пробелы группировки и десятичную запятую.
Даты сохраняются без сдвига часового пояса и не обязаны попадать в отчётный период.
Формулы читаются по сохранённому Excel результату, без выполнения формул и открытия
внешних книг. Если результата нет или ячейка содержит ошибку, загрузка отклоняется;
файл нужно пересчитать и сохранить в Excel.

`POST /api/incoming-reports/import`, `multipart/form-data`, часть `file` — загрузка книги.
Ответ 200 содержит `filename`, ID типов, периода и предприятия, их наименования,
`totalRows`, `totalValues` и `sheets` с кодом листа, ID формы, количеством строк/значений
и фактическим диапазоном строк Excel. Ошибка файла или ячейки — 400 `INVALID_REQUEST`,
превышение размера — 413. Сообщения о данных содержат лист и координату ячейки.

Весь файл сохраняется одной транзакцией: ошибка любого листа откатывает **все** листы,
включая уже отправленные в БД пакеты. Заголовки и вертикальные группы записываются
в `TB_REFERENCE_ITEM`, значения полей — в `TB_REFERENCE_ITEM_VALUE` с исходными
номерами строк и связями с метаданными. Если у формы за этот период и предприятие
уже есть записи в `TB_REFERENCE_ITEM`, файл отклоняется с 409 `DATA_CONFLICT`;
перезапись и объединение с существующими данными пока не поддерживаются.

Импорт не изменяет `MD_*` и `DR_*`. Для согласованности используется временная
блокировка существующих строк типов периодов (`SELECT FOR UPDATE`), общая для
импорта и изменения метаданных; параллельные импорты выполняются последовательно.
После успешной загрузки существующее правило защиты метаданных определяет пару
как доступную только для просмотра. Дополнительный статус не записывается.
Миграция БД не нужна; требуются обновление frontend и перезапуск backend.

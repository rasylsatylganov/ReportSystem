# Универсальная система отчётности

Java 21, Maven, Spring Boot 3.5.6, Oracle. Проект содержит два Maven-модуля.

| Модуль | Содержимое |
|---|---|
| `common` | Entity, репозитории и сервисы системы отчётности |
| `web-api` | REST-контроллеры, DemoApplication, настройки и тест приложения |

Зависимость: `web-api` использует `common`. Корневой POM объединяет модули.
`common` собирается в обычный JAR, `web-api` — в запускаемый Spring Boot JAR.

## Модели и сущности

JPA-сущности находятся в `common/.../entity` и имеют суффикс `Entity`.
Контроллеры и публичные интерфейсы сервисов используют records из
`common/.../model`: например, `DrTypePeriod` для ответа и
`DrTypePeriodRequest` для создания или изменения записи.

Преобразование выполняют классы `...Mapper` из `common/.../mapper`.
Сервисы вызывают их внутри своих транзакций и отвечают за операции с
репозиториями. В ответах связанные записи представлены вложенными моделями;
мапперы преобразуют JPA-связи, не обращаясь к другим сервисам.
В запросах связи задаются через `IdReference`, например
`"typePeriod": {"id": 1}`. `JpaReferenceResolver` получает управляемую JPA-ссылку по ID;
остальные поля вложенного объекта не изменяют связанную запись.

ID новой записи назначает backend; при обновлении используется ID из URL.
Порядок типов периодов также назначает backend: входная модель не содержит
`sortIndex`. Названия полей JSON и URL существующих маршрутов сохранены.

## Валидация запросов и ошибки API

Входные records `...Request` проверяются через Jakarta Bean Validation
и `@Valid` в контроллерах. Проверяются обязательные значения, длины строк,
точность чисел, положительные ID и номера строк/столбцов, вложенные ссылки.
Дата окончания периода не может быть раньше начала; диапазон строк импорта
также должен иметь согласованные границы.

Ошибки обрабатывает `web-api/.../exception/GlobalExceptionHandler`.
Все ответы об ошибках имеют поля `code` и `message`, например:

```json
{"code":"VALIDATION_ERROR","message":"Поле «Код типа периода» обязательно."}
```

HTTP-статусы: 400 — ошибка запроса, 404 — ресурс не найден,
409 — конфликт ограничений данных, 500 — неожиданная ошибка сервера.
Некорректные методы и Content-Type возвращают соответственно 405 и 415.
Сообщения для клиента не содержат stack trace или деталей SQL/БД.
Доменная ошибка отсутствия записи представлена `ResourceNotFoundException`,
некорректной внутренней ссылки — `InvalidRequestException`.

## Oracle

Все 13 JPA-сущностей наследуют `BaseEntity` с полями `createdAt` и
`updatedAt`, которые хранятся в столбцах `CREATED_AT` и `UPDATED_AT`.
При вставке обе даты заполняются одинаковым текущим временем; при
изменении обновляется только `updatedAt`. Используется `Asia/Bishkek`.
Заполнение выполняют JPA callbacks `@PrePersist` / `@PreUpdate`.

Перед первым запуском этой версии остановите backend и выполните
`docs/sql/001_add_audit_timestamps.sql` в той же схеме Oracle, к которой
подключается приложение (SQL Developer: Run Script / F5; также SQLcl/SQL*Plus).
Скрипт добавляет столбцы `TIMESTAMP(6)`, заполняет пустые значения у старых
записей и устанавливает `NOT NULL`. Для старых записей без дат используется
время миграции: фактическое время их создания восстановить невозможно.
Повторное выполнение сохраняет уже заполненные даты. Oracle DDL выполняет
автоматический commit, поэтому миграция не является одной транзакцией.

Прямые SQL-операции и массовые JPQL-обновления обходят JPA callbacks:
при таких операциях даты нужно заполнять явно. Поля аудита не принимаются
во входных Request-моделях и не добавлены в текущие JSON-ответы.

Исходный `application.properties` без изменения содержимого перенесён в
`web-api/src/main/resources/application-local.properties`.
Он подключается автоматически через `spring.config.import`; активировать
профиль вручную не требуется. Исходные настройки подключения и JPA сохранены.

Локальный файл исключён из Git. После клонирования репозитория на другом
компьютере создайте его по образцу `application-local.properties.example`
или восстановите собственную локальную конфигурацию.
Файл-пример использует переменные `ORACLE_JDBC_URL`, `ORACLE_USERNAME`,
`ORACLE_PASSWORD`.

## Сборка и запуск

Все команды выполняются из корневой папки, где находятся оба модуля.
Требуются установленные JDK 21 и Maven, доступ к Maven-репозиториям.

Сборка без запуска исходного теста, подключающегося к Oracle:

```shell
mvn clean package -DskipTests
java -jar web-api/target/web-api-0.0.1-SNAPSHOT.jar
```

Полная сборка с исходным `@SpringBootTest` (требует доступную Oracle
и корректную конфигурацию):

```shell
mvn clean install
```

Запуск из Maven после установки модулей:

```shell
mvn install -DskipTests
mvn -pl web-api spring-boot:run
```

При первом запуске из IDE Maven-проекты должны быть импортированы вместе.

## Пагинация справочников

`GET /api/dr-enterprises`, `/api/dr-periods`, `/api/dr-references`,
`/api/dr-reference-items`, `/api/dr-type-periods` и `/api/dr-type-enterprises`
принимают query-параметры `page` (от 0, по умолчанию 0)
и `size` (от 1 до 100, по умолчанию 20). Записи выбираются страницами в БД
с сортировкой по `id` по возрастанию; типы периодов и предприятий — по `sortIndex`, затем `id`.
Некорректные параметры дают HTTP 400.

Пример: `GET /api/dr-enterprises?page=0&size=20`.

Ответ содержит `content` (массив моделей), `page`, `size`, `totalElements`
и `totalPages`. Пустая коллекция имеет `totalPages: 0`; страница за пределами
списка возвращает HTTP 200 с пустым `content` и фактическими итогами.
Это изменение контракта: потребителям всех шести маршрутов нужно читать
`content` вместо массива в корне ответа и запрашивать необходимые страницы.

Страницы типов периодов и типов предприятий на frontend загружают данные с сервера по страницам,
показывают общее количество записей и предлагают размер страницы 10, 20, 50 или 100
(по умолчанию 20). Перемещение записи через границу страницы открывает целевую
страницу; удаление последней записи страницы возвращает на существующую страницу.

## Справочник типов предприятий

На frontend в меню «Справочники → Типы предприятий» добавлена страница
`/type-enterprises`: создание, редактирование, удаление, серверная пагинация
и перестановка записей вверх/вниз. Код ограничен 50 символами, наименование — 200.

Перед запуском обновленного backend остановите его экземпляры и выполните
в Oracle-схеме приложения `docs/sql/002_add_type_enterprise_sort_index.sql`.
Скрипт добавляет `DR_TYPE_ENTERPRISE.SORT_INDEX NUMBER(19,0) NOT NULL`,
заполняет отсутствующие значения из `ID` и подготавливает последовательность
`DR_TYPE_ENTERPRISE_SORT_SEQ` выше максимального существующего индекса.
Повторный запуск сохраняет заполненные индексы и не перемещает последовательность назад.
Oracle DDL автоматически фиксирует изменения; миграция не является единой транзакцией.

Поле `sortIndex` возвращается в модели, назначается сервером и не редактируется
через POST/PUT. Новые записи добавляются в конец. Для перестановки используются
`POST /api/dr-type-enterprises/{id}/move-up` и `.../{id}/move-down`.
Операции изменения блокируют записи справочника в порядке ID в транзакции;
перестановка сохраняет обе измененные записи явно. Граница списка возвращает 204
без изменения данных; отсутствующая запись — 404; конфликт данных — 409.
